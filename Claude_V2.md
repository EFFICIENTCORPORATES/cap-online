**Author:** CA Pranav Pratik Tulshyan — AIR 1 (CPT) · AIR 1 (IPCC) · Faculty, VC Gurukul, Noida
**Target reader:** 17–19-year-old commerce student fresh out of CA Foundation; heavy social media exposure, short attention span. Must also work for someone in panic mode 20 days before the exam.

## 3. Routing Page

**The whole guide runs SUBJECT BY SUBJECT.** Each subject sits in its own bucket. Ask "which bucket" once per subject, not once for all of CA. True even for both-groups students.

Routing options A–G:
- A → not started yet → Bucket 1 (+ Bucket 0 alongside from day 1)
- B → mid-classes → Bucket 2 (read B0 + B1 this weekend)
- C → classes done, in revision → Bucket 3
- D → 45 days away or less → Bucket 4
- E → exam starts in days or is on → Bucket 5
- F → exams over, waiting for result → Bucket 6
- G → 10 days or less, just need to pass → Emergency Section

**Repeat attempt self-check (per subject):**
- 70%+ concepts clear → Bucket 3
- 50–70% → Bucket 2
- Under 50% → fresh start at Bucket 1 (+ Bucket 0)

### EMERGENCY SECTION (standalone, fully independent)

For: 10 days left, just need to pass (40 a paper). Points to nothing else.

**6 steps:**
1. Triage every subject (Day 1 ~30 min each): find 3–4 chapters carrying 50–60% of marks. Those only.
2. No notes? Use ICAI Study Material illustrations (not the text).
3. MCQs are the fastest marks. Read priority chapter summary once, attempt MCQs, know why wrong is wrong.
4. 10-day schedule: Day 1 = triage. Day 2–7 = priority chapters only (morning practical, evening theory, 2 subjects max, illustrations + MCQs per chapter). Day 8 = revise all covered, one-page sheets per chapter. Day 9 = error-prone areas + format/formula recall. Day 10 = light revision only.
5. In the hall: attempt SOMETHING for every question. Format headings. Approach statement. Partial marks across 8 questions at 3–5 = 24–40 before a single full answer.
6. What NOT to do: no new books/PDFs, no full-syllabus attempts, no discussing prep, no skipping sleep, no checking what others study.

## 6. Key locked decisions and rules

- **Boundary system:** MIN/MAX/RANKER defined. 3-question filter before adding anything. Golden Rule: if can't revise before exam, don't add it. 3 revisions mandatory for anything inside the boundary.
- **3-Layer system:** Layer 1 (classes) → Layer 2 (revision) → Layer 3 (45 days out). NEVER build Layer 2 during Bucket 2. Layer Lock Rule is the most common structural mistake in the book.
- **Energy matching (FLIPPED from conventional advice):** Theory in your peak window (whenever that is). Practical sums when low/sleepy. Not the other way.
- **Mnemonics rule:** Revision ALWAYS mnemonic + its trigger question together. A floating mnemonic is worse than none.
- **Layer 3 test:** Can read full subject in 30–40 minutes. If longer, it's turning into Layer 2.
- **Layer 3 is NEVER digital primary.** Physical, always.
- **Error Register type 2 — Lucky Right:** always enter. A lucky right is a future wrong.
- **Notebook prefix:** P01, P02, P03 for both physical notebooks AND digital files.
- **One group vs both:** Worked out from backward-planning hours. If the plan only fits at flawless zero-buffer execution, take one.
- **Between-paper day:** 20–22 usable hours. Not a rest day. Fully structured.
- **Dropped strategies:** Five-Year Rule, Articleship Discipline, rigid Pomodoro mandates, 1-1-1 rule, 24-hour rule.
- **Phone strategy:** Second Space / New User — not "delete social media."
- **Journaling:** WhatsApp group with yourself + voice notes — not written diary.
- **End Goal format per bucket:** One tick-list at the START (done when → checklist). No separate closing checklist. Bucket 0 has Daily Tick instead.

## 13. Learnings — paged.js architecture + multi-file book assembly (2026-07-22)

Read this before touching `tools/strategy_book_parser.py`, `tools/strategy_book_merge.py`,
or anything under `design/templates/build/`. These are hard-won, verified findings
(tested with headless Chrome `--dump-dom`, not assumed) from wiring paged.js into
the per-section generator and designing the whole-book merge script.

### 13.1 Why the old fixed-page-div pattern was actually broken

The original generator put each section's running header/edge-tab/journey-strip as
`position: absolute` children of one big per-file `.page-shell` div. This looked
right for exactly one physical page, but silently failed the moment a bucket's
content was long enough that Chrome would slice it into multiple PDF pages — the
header/footer/edge-tab would only ever appear once per file, not once per physical
page. **Lesson: anything meant to repeat "per printed page" cannot be positioned
relative to one big content div — it needs to be a CSS Paged Media running element.**

### 13.2 The correct mechanism: `position: running()` + `@page` margin boxes

Define the header/edge-tab/footer markup **once per section**, tag each with
`position: running(name)`, then reference it from `@page { @top-center { content:
element(name); } }` (or `@right-middle` for the edge tab, gated to `@page :right`
so it only shows on recto pages). Paged.js (not native browser printing) implements
this polyfilled CSS Generated Content for Paged Media spec — it clones the running
element onto every generated physical page automatically. No JS, no manual repeat.

**This same mechanism is what makes whole-book merging work almost for free:**
running elements update their "current value" at the point in the document flow
where they're redefined — exactly like a real book's chapter-name running header.
Concatenate Bucket 0's content, then Bucket 1's (which redefines the same three
running-element names with its own color/label), and the header/edge-tab/footer
correctly "switch over" the moment the reader crosses into Bucket 1. **Do not
uniquify these names per section** (e.g. `running(bucket1Header)`) — that would
break the whole point.

### 13.3 `@page` does not reliably resolve `var()`

Chrome/paged.js should not be assumed to resolve CSS custom properties inside the
`@page` rule's `size`/`margin` descriptors. Fix used here: `design/page-geometry.json`
is the single source of truth; `get_css()` in the parser substitutes its literal
values into BOTH the `:root` block (for everything else, where `var()` works fine)
AND the `@page` rule (as literals) at generation time — never hand-duplicate these
numbers, never assume `var()` will work in `@page`.

### 13.4 The PDF-export gap: paged.js needs screen media, plain `--print-to-pdf` doesn't give it

Verified 2026-07-22: `chrome --headless --print-to-pdf` on a paged.js file produces
a near-empty (~1KB) PDF even with a generous `--virtual-time-budget`. Paged.js's
paginated output is only reliably captured in **screen** media; plain Chrome CLI
flags have no switch for this. `--dump-dom` (which doesn't force print media)
confirmed the pagination itself was correct — the bug was purely in the capture
step. Two fixes, no in-between: (a) manual — open in Chrome, let paged.js finish,
Ctrl+P → Save as PDF (works with zero new tooling, chosen path for now); (b)
automated — Node + Puppeteer with `page.emulateMediaType('screen')` called before
`page.pdf()`, plus waiting for paged.js's `rendered` event rather than a fixed
timer. **Node/npm are not installed on this machine** — do not install without
asking first. Full detail: `_claude/skills/SKILL-html-to-pdf.md` §9.

### 13.5 Merging independent section files into one book — verified, not assumed

Confirmed by diffing the embedded `<style>` block across 4 different generated
files (`bucket-0`, `ai-section`, `cover`, `authors-journey`): **byte-identical**.
`get_css()` only depends on page geometry, never on section color/label — those
are always inline styles on elements, never baked into the shared stylesheet. This
means consolidating to one shared stylesheet when merging sections is provably
lossless, not just visually similar.

**A real, verified bug found while checking mergeability:** every strategy heading
gets `id="s{number}"`, and that number restarts at 1 in every bucket (confirmed:
`bucket-0.html` and `bucket-1.html` both contain `id="s1"`, `id="s2"`...).
Concatenated as-is, a merged book would have duplicate IDs everywhere — invalid
HTML, and any internal anchor to `#s3` would only ever resolve to the first
bucket's strategy 3. **`strategy_book_merge.py` prefixes every such id with its
section slug** (`id="bucket-1-s3"`) while stitching — this is the one correctness
fix that must never be skipped.

**Everything else a whole-book merge script must get right** (see
`tools/strategy_book_merge.py` for the implementation, which handles all of these):
- Take the CSS, Google Fonts `@import`, and paged.js `<script>` tag **exactly
  once** — concatenating them per-section would re-initialize paged.js repeatedly
  on the same document and could corrupt its own pagination output.
- One deliberate `<title>` for the merged file, not whatever the last section
  happens to leave behind.
- The merged file must be written into the **same folder** as
  `vendor/paged.polyfill.js` (i.e. `design/templates/build/`) or the existing
  relative script path breaks silently — no error dialog, paged.js just never runs.
- `break-before: right` (forces each section onto a fresh right-hand/recto page)
  isn't present in the individual per-section files — it must be injected only at
  merge time, wrapping each section's fragment.
- Book order lives as an explicit ordered list/tuple of slugs in the merge script
  (or passed via CLI), **not** derived from filenames — safer against reordering
  mistakes than renumbering 14 files whenever the book's structure changes. The
  script cross-validates the tuple against what's actually in `build/` in both
  directions: missing file for a listed slug = hard error; a generated file that
  exists but isn't in the tuple = loud warning (protects against a section
  silently vanishing from the final book).
- Explicit `encoding='utf-8'` on every read/write, matching the existing
  generator's discipline (this repo has a documented history of cross-mount
  encoding corruption — see CLAUDE.md's non-negotiable UTF-8 rule).
- **Verify with `--dump-dom`, never trust by reading the code alone** — this is
  what caught both the original page-shell bug and the print-media export gap;
  the same discipline applies to the merge script's output before it's trusted.

## 14. Second-round learnings — footer bug, a real ongoing hazard, current geometry, print-dialog settings (2026-07-22)

### 14.1 A real bug found and fixed: journey-strip rendered as a vertical column, not a row

Confirmed by taking an actual headless-Chrome **screenshot** (`--screenshot`, not just `--dump-dom` — dump-dom shows the DOM is right but not how it visually lays out; for a layout bug you have to actually look) — the `.journey-strip` footer (the `0 1 2 3 4 5 6 AI EMG` segments) was stacking vertically instead of horizontally once cloned into the `@page @bottom-center` margin box.

**Root cause:** paged.js has a known quirk where content cloned into a `@page` margin box via `content: element()` can pick up an inline style during that clone that forces block layout, silently beating a plain (non-`!important`) class rule.

**Fix (already applied in `tools/strategy_book_parser.py`'s `get_css()`):** `.journey-strip` now sets `display: flex !important; flex-direction: row !important; flex-wrap: nowrap !important;` — `!important` is the one thing that reliably wins over an injected inline style. Also gave the `@bottom-center` margin box an explicit `width: 55mm` so paged.js doesn't auto-narrow it.

**Lesson: any CSS applied to a `position: running()` element that will be cloned into a `@page` margin box should be written defensively with `!important` on layout-critical properties (display/flex-direction/flex-wrap), and verified with an actual screenshot, not just DOM inspection.** A secondary, not-fully-understood observation: on page 1 specifically, the segment strip appeared to render twice (once near the top, once at the correct bottom position) — not confirmed as a recurring problem on interior pages, flagged for future attention if it resurfaces.

### 14.2 Ongoing hazard: multiple build/ files carry hand-authored content NOT in MASTER.md — DO NOT run blanket `--section all` on any file without checking first

This is the single most important operational risk in the current setup, and it has now bitten us **twice** — once recoverably (front-matter.html, 2026-07-22), once **not** (authors-journey.html, 2026-07-23 — the actual written prose was lost for good; see project_log.md for that date).

**What happened (front-matter, 2026-07-22):** a concurrent editor (a "parallel AI" also writing into this repo, per Pranav) added a fully hand-crafted Title Page + Copyright Page directly into `build/front-matter.html`, bypassing MASTER.md entirely. An assistant mistake (`--section all` run right after being told to leave the file alone) destroyed it; recovered only because the exact removed text was still visible in an earlier diff within the same conversation.

**What happened again (authors-journey, 2026-07-23):** the same concurrent editor separately wrote a full 5-phase first-person narrative into `build/authors-journey.html` (logged in project_log.md as "Author's Journey ... complete"). A **later** blanket regeneration (run twice, across two different fixes in the same session, neither of which specifically checked this file) silently reverted it to the placeholder. This time there was no diff in context to recover from — the content was genuinely gone, and had to be rewritten from scratch (from `books/about-author/Pranav_Pratik_Tulshyan_Master_Profile_Journey.md`, the real source material, still intact) rather than restored.

**The lesson from the second incident: knowing about ONE hand-edited file is not enough.** Protecting `front-matter.html` specifically, while still blanket-regenerating "the other 13 sections," is exactly what let authors-journey.html get destroyed — there was no reason to assume only one file had been hand-edited by a concurrent session, and there wasn't.

**Standing rule until this is resolved properly:** before running `tools/strategy_book_parser.py --section all` (or any single `--section`), check **every** file that would be touched for divergence from a fresh regen — not just the ones already known to be hand-edited. A quick way: regenerate each into a temp path and diff, or at minimum compare file mtimes across all `build/*.html` files (files touched by a concurrent hand-edit will have a distinctly newer mtime than the rest). Do not assume the set of hand-edited files is closed just because you've found one or two of them before.

**Real fix, not yet done:** port all hand-authored content (front-matter's Title/Copyright pages, authors-journey's narrative, and any others not yet discovered) back into MASTER.md as the actual source of truth, so it stops being invisible to the generator. Until then, this class of silent data loss remains possible on every regeneration.

**Real fix, not yet done:** port the hand-authored Title Page/Copyright Page content back into MASTER.md's `FRONT MATTER` section as real markdown (may need a small addition to the parser's component vocabulary, since the current tokenizer has no "title page" or "copyright page" component type — it would need one, or these could stay as a documented, deliberate exception that's hand-patched after every regeneration rather than generated).

### 14.3 Current page geometry (as of 2026-07-22, narrowed from the original design-spec values)

`books/strategy-book/design/page-geometry.json` currently holds:
```
top: 14mm · bottom: 16mm · inner: 16mm · outer: 16mm
```
(narrowed from the original design-spec.md values of top 20mm / bottom 24mm / inner 22mm / outer 25mm, at Pranav's request, to reduce page count/print cost). **Trade-off knowingly accepted:** design-spec.md's 25mm outer margin was originally sized to hold both the 12mm edge tab *and* pencil-note space for the student; at 16mm outer, the dedicated note space is much thinner (still fits the edge tab, thin margin left for notes, not truly gone but reduced). If margins need adjusting again, it's one JSON edit + regenerate — but remember section 14.2's hazard when regenerating.

### 14.4 How to actually print this correctly via Chrome's manual Ctrl+P path

Verified against a real print-dialog screenshot Pranav sent — two settings were silently fighting the book's own design:

- **Destination must be "Save as PDF," not "Microsoft Print to PDF."** The latter routes through a Windows print driver, which only supports a fixed list of standard paper sizes (A4, Letter, ...) — it cannot honor this book's custom 177.8×254mm trim, so the content renders inside a larger sheet with padded empty space around it. "Save as PDF" is Chrome's own internal PDF export and respects the page's actual CSS-declared `@page` size.
- **"Headers and footers" must be unchecked.** Checked, it adds Chrome's own native print header/footer (date/time, page title, URL, page number) on every page, layered on top of the book's own paged.js-rendered running header/footer — this is what produced visible clutter like "7/22/26, 8:40 PM ... file:///D:/...FULL-BOOK.html ... 18/92" on every page.
- **Margins should be "None," not "Default."** Chrome's own print-margin setting is separate from and additive to the book's `@page`-declared margin — "Default" adds Chrome's own inset on top of what's already rendered.
- **"Background graphics" should stay checked** — that one's correct; it's what makes bucket colours print instead of white.

### 14.5 Verification technique added this session: headless Chrome `--screenshot`

Beyond `--dump-dom` (confirms DOM/pagination structure) and `--print-to-pdf` (confirms the export path), a plain visual `--screenshot` flag (`chrome --headless=new --window-size=W,H --virtual-time-budget=N --screenshot=out.png <file-url>`) is worth reaching for whenever a *layout* bug is suspected (rows collapsing into columns, elements overlapping, spacing looking off) — DOM structure can be perfectly correct while still rendering wrong, and only an actual rendered image catches that. This is how the 14.1 bug was confirmed, both before and after the fix.

## 15. Critical lesson: `--dump-dom` / `--virtual-time-budget` are NOT reliable ways to check whether paged.js has finished on a large merged document (2026-07-22)

This cost a lot of debugging time and is worth getting right in any future session.

**What happened:** after excluding "cover" from `BOOK_ORDER` (Pranav's explicit order) and re-merging, repeated `chrome --headless=new --virtual-time-budget=N --dump-dom` calls on the *same unchanged* `FULL-BOOK.html` gave wildly different `.pagedjs_page` counts across runs — 4, then 7, then 10, then 22, then 262. This looked exactly like a real, serious pagination bug.

**False leads chased and ruled out:**
- Suspected the empty `.blank-page` div (forced `break-after: page`, zero content) was confusing paged.js's fragmentation. Removed it experimentally — instability persisted (4, 7, 4, 10). Not the cause.
- Suspected Google Fonts loaded via network `@import` racing against paged.js's layout pass (a real, plausible mechanism, and worth fixing regardless). Vendored all fonts locally (`design/templates/vendor/fonts/` + `gfonts-local.css`, loaded via `<link>` instead of `@import` — see below). Instability *persisted even with local fonts* (262, 16, 13, 7, 43). Not the (sole) cause.

**Actual cause, confirmed properly:** `--dump-dom` captures the DOM whenever Chrome's headless "page ready" signal fires (roughly the `load` event, or whenever `--virtual-time-budget` simulated time runs out) — **not** whenever paged.js has actually finished. For a small file (one bucket) this coincides closely enough with real completion that it doesn't matter. For a ~200KB, 13-section merged book, paged.js needs **real CPU-bound wall-clock time** (observed: comfortably under 20s, but nowhere near instant) to finish laying out ~87 pages — and every `--dump-dom`/`--virtual-time-budget` combination tried was simply catching it at a different, arbitrary, mid-render point every time. `--virtual-time-budget` in particular does not reliably extend real time for CPU-bound synchronous/microtask JS work the way it does for timers/network — it appears to also introduce its own nondeterminism into paged.js's internal rAF-based convergence loop, which is why the same document produced whatever count depending on the (essentially arbitrary) budget value.

**How this was actually confirmed, properly, this time:** installed `websocket-client` via pip (flagging as an environment change, same as the other concurrent session's `pypdf`/`cryptography` install this same day — low-risk, easily redone) and drove Chrome directly over the DevTools Protocol: launched headless Chrome with `--remote-debugging-port=9222 --remote-allow-origins=*`, opened the file as a real tab, and polled `document.querySelectorAll('.pagedjs_page').length` every 3 real seconds (genuine `time.sleep()`, no virtual time involved at all). Result: **87 pages, already stable at the very first check, unchanged for the full 120 seconds of polling.** Separately confirmed the actual rendered text ends exactly where the book's real content ends ("End of Master Draft. All buckets and sections collected...", the true final line of the Author's Journey section) — nothing was silently truncated.

**Standing rule for future verification of this document:** do not trust a single `--dump-dom` or `--screenshot` capture's page count for the *full merged book* as evidence of anything, since it may simply have been caught mid-render. Either (a) poll for stability over real wall-clock time (repeat the check every few real seconds until the count stops changing, as above), or (b) simplest and matches the actual user workflow anyway: open it in a real, foreground Chrome tab and visually wait until scrolling/the page stops visibly changing before trusting what you see — a human naturally does this; a one-shot headless capture does not. This does *not* invalidate every `--dump-dom` check done earlier in this session for *single-section* files (bucket-0.html etc.) — those are small enough to render well within a few seconds, so the same risk doesn't apply at that scale.

**Kept regardless, as a genuine improvement independent of the above:** fonts are now vendored locally (`design/templates/vendor/fonts/*.woff2` + `gfonts-local.css`, referenced via `<link rel="stylesheet" href="../vendor/gfonts-local.css">` in every generated file's `<head>`, replacing the old `@import url('https://fonts.googleapis.com/...')`). Removing the network dependency is strictly better for reliability and offline-safety even though it wasn't the root cause of the instability — same principle as vendoring paged.js itself.

**Important — these font files are NOT git-tracked** (`.woff2` is binary; this repo's explicit rule is no binaries in git). Run `python tools/fetch_local_fonts.py` once after cloning (or any time `design/templates/vendor/fonts/` is missing) to regenerate both the font files and `gfonts-local.css` together — they're deliberately regenerated as one matched pair rather than committing the CSS separately from the binaries it references, exactly like `design/templates/build/` itself is regenerated from MASTER.md rather than committed.

**Current confirmed state:** `FULL-BOOK.html` (order: front-matter, routing, bucket-0..6, ai-section, emergency, personal-pages, authors-journey — "cover" deliberately excluded per Pranav) paginates correctly and stably to **87 pages**.
