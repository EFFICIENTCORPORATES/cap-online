Starting point

What capranav.com actually is today

Read through the whole site before drafting anything below. It's a fully static bundle — plain HTML, CSS and JS, no framework, no build step, no server — shipped straight to Cloudflare Pages (README.txt literally says "upload the complete contents of this folder"). There is no login, no user record anywhere, and no payment code. That's not an oversight — policies.html's own Refund section says so directly: "This static website does not itself collect course payments. Where a course is purchased through an external enrollment provider, the refund and cancellation terms displayed by that provider at the time of purchase apply." Today, capranav.com markets and teaches for free; a separate provider handles enrollment and money.

That means everything in this plan — accounts, a paywall, a protected reader, checkout — is genuinely new infrastructure, not a tweak to something half-built. Good news: this repo already runs a comparable system for the Telegram bot platform (login-free OTP flows, a shared database, branded PDF generation, Cloudflare email sending), so the pattern is proven, just not yet pointed at this site.

01 · Accounts

Signing in

Email + one-time code, nothing else. Students already know this pattern from the Telegram bots' contact verification.

  1. Student enters their email on any "Read this book" or "Buy" button.
  2. A 6-digit code is emailed (Cloudflare Email Service), valid 10 minutes, one active code per address at a time.
  3. Correct code sets a signed session cookie. No password, ever, means nothing to leak or reset.
  4. Returning students who purchased before just enter their email again — the session, not a purchase receipt, decides what unlocks.

02 · The Vault

A book you can read but not take

This is the real engineering problem, and it's worth being honest up front: no method makes a screen un-photographable. The goal here is to make casual copying — save-as-PDF, right-click-save, sharing the file — genuinely hard, and to make anything that does leak traceable back to the one account it was shown to. That's the strongest practical option, which is what you asked for.

  • Source PDF stays private

    The finished, watermarked book (this repo already produces exactly this shape of file for the Question Bank Book) is uploaded once to the private R2 bucket. It is never linked, never served whole, never has a public URL.

  • Every page becomes an image

    Each page is rendered to a high-resolution image ahead of time and cached in R2 — the same idea as this repo's existing print-watermarking script, run per-page instead of per-book.

  • The viewer checks who's asking

    A Pages Function looks up the signed-in session, checks the entitlements table for that book, and only then allows the request to proceed.

  • A personal stamp is burned into the pixels

    At request time, the reader's name, email, order ID and a timestamp are overlaid on the page image as a faint diagonal tile before it's sent — not stored that way, generated fresh per view. A page that leaks points at exactly one buyer.

  • Pages arrive one at a time, briefly

    The front-end reader fetches each page image through a link that expires in roughly a minute, just ahead of where the student is scrolling. The whole book is never sitting in one downloadable response.

  • The page itself resists the obvious shortcuts

    Right-click, text selection, browser print and Ctrl+S are disabled; a page-visibility check dims the reader if dev tools open. Deterrents, not guarantees — stated as such in the Terms.

    • Why images, not an embedded PDF

    A real PDF file — even inside a locked-down viewer — is one "inspect element" away from a direct URL. Rendered, watermarked, short-lived images close that gap and double as a leak trace. The cost is engineering effort up front (the render pipeline) and slightly more server work per page view, both one-time or marginal.

    Built into the Vault

    The free sample chapter

    Same pipeline, one flag flipped. Every book gets a configurable demo_page_count (you mentioned 5–10 pages) stored alongside it. Requesting a page inside that range skips the entitlement check entirely — no login, no payment — and requesting anything beyond it redirects to sign-in-or-buy. This is one code path, not a separate viewer, so it can never drift out of sync with the paid version.

    One open question below: whether the demo stays fully anonymous, or asks for an email first (still free) so a demo reader becomes a lead you can follow up with.

    03 · Checkout

    Paying and unlocking

    1. Student taps Buy. A pending order is written to D1 with a Razorpay order ID.
    2. Razorpay's checkout overlay opens — UPI, card, netbanking, wallets.
    3. Razorpay calls back a Pages Function webhook. The signature is verified before anything else happens.
    4. On a confirmed payment, an entitlement row is written for that student and book. The order ID is the uniqueness key, so a retried or duplicate webhook can never grant a second entitlement.
    5. The student is dropped straight back into the reader, now unlocked — no separate "check your email for access" step.

    Foundations

    What the new database holds

    One new D1 database, capranav_platform, entirely separate from the Telegram platform's platform.db.

    TableHolds
    usersEmail, display name, created-at. No password field — there isn't one.
    otp_codesShort-lived login codes, one active per email, expiry timestamp.
    sessionsSigned session tokens issued after a correct code.
    booksTitle, price, source file reference, page count, demo_page_count.
    ordersRazorpay order ID, student, book, amount, status (pending / paid / failed).
    entitlementsWhich student can read which book — the one table the viewer actually checks.
    viewer_access_logEvery page served: who, which book, which page, when — the forensic trail behind the watermark.
    courses / course_entitlementsPhase 2 — same shape as books/entitlements, applied to video.

    04 · Phase two

    Courses, once the Vault is proven

    The accounts and entitlements system carries over unchanged — a course purchase is the same order-and-unlock flow as a book, just pointed at video instead of pages. The one new piece is video delivery: Cloudflare Stream is the natural fit here since it stays in the same account and account bill, supports signed playback URLs and domain-locking the same way the Vault locks page images.

    This section is deliberately light — course structure, pricing and whether any video content actually exists yet aren't decided (see below). The architecture is designed so this slots in without touching the book system.

    Housekeeping

    What has to change in Policies

    policies.html is written for the current world, where an external provider handles money and access. Three sections stop being accurate the day this ships and need a rewrite, not a patch:

    • Refunds — currently disclaims collecting payment at all. Needs a real digital-goods refund policy once capranav.com is the seller of record.
    • Course Access — currently points at "the enrollment terms shown at purchase" from a third party. Needs to state the account/entitlement model directly.
    • A new fair-use clause — should say plainly that books are licensed for personal reading, not redistribution, and that copies are watermarked to the buyer. Sets expectations honestly rather than overpromising protection this plan can't actually deliver.

    What only you can decide

    Which book launches first — the pilot in Phase 2?

    Price per book, and any bundle pricing across the Strategy Book / Concept Book / Question Bank Book?
    Needed before Phase 3's real test payment.
    Does the free demo require an email first, or stay fully anonymous?
    Recommend requiring email — still free, but turns sampling into a list you can follow up with, at the cost of one extra tap.
    Exact demo length per book — flat 5–10 pages, or does it vary by book size?
    A flat count is simplest to configure; a proportional cut (e.g. first 5%) may read fairer for a very long book.
    Refund terms for a digital book once a purchase unlocks the full reader?
    Common practice for digital goods is no refund once the paid pages have been opened — needs your explicit call, since it goes directly into Policies.
    Does this replace the existing external-provider enrollment, or run alongside it for existing courses?
    Affects how much of policies.html's current wording can stay versus needs replacing.
    For courses — is there real video content ready today, or is Phase 5 purely a placeholder for later?
    Determines whether Phase 5 gets scoped in detail now or genuinely waits.
