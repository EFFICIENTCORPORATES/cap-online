> **What this is:** cap-online is CA Pranav Pratik Tulshyan's CA Inter Advanced Accounting
> teaching ecosystem (VC Gurukul, Noida). One of its six pillars is the **Question Bank
> Book** — a student-facing reference that collects every past MTP/RTP/PYQ exam question,

> annotations, ultimately rendered as one HTML book per syllabus chapter and merged into a

## 1. The end product

One HTML book per AS/chapter (e.g. `AS10_Question_Book.html`), each collecting every
question across every MTP/RTP/PYQ sitting that tests that chapter — official answer,
topic tags, Common Student Mistakes, all as verbatim, source-faithful content. See
`books/question-bank/metadata-index/AS10_Question_Book.html` for the hand-built quality
bar every automated output is measured against.

## 2. The pipeline, in order

```
Raw PDF (per sitting)
   │  read directly, PDF not MD — see SKILL-question-bank-verbatim-extraction.md
   ▼
Sitting HTML (permanent primary record, one per paper)
   │  schema — see SKILL-question-bank-html-schema.md
   │  topic tagging — see SKILL-question-bank-topic-tagging.md
   │  independent-question splitting — see SKILL-question-bank-question-splitting.md
   │  Common Student Mistakes — see SKILL-question-bank-examiner-comments.md
   ▼
questions.json (machine index, one row per question/fragment)
   │  built by first_run/scripts/extract_questions.py (BeautifulSoup) — built 2026-07-25
   │  duplicate/recurring-question detection — see SKILL-question-bank-duplicate-detection.md (still not built)
   │  difficulty (easy/medium/hard) computed here, not authored in HTML — see §4 below
   ▼
Chapter-wise HTML books (one per AS/chapter, 34 total, MCQs excluded)
   │  generated by first_run/scripts/generate_chapter_book.py + generate_all_chapter_books.py
   │  see SKILL-question-bank-chapter-book-rendering.md
   ▼
Front matter, Table of Contents, Back matter
   │  generate_qb_front_back_matter.py, generate_qb_toc.py — standalone reviewable HTML files
   ▼
Whole-book HTML (front matter + ToC + 34 chapters + back matter, merged)
   │  qb_merge.py — reuses tools/strategy_book_merge.py lessons, see CLAUDE.md §7
   │  for the print/page-break architecture this follows
   ▼
Real page numbers resolved, ToC patched, re-merged
      resolve_qb_toc_pages.py --remerge — the only step needing a real (headless) browser
```

**Full command sequence and every gotcha**: `first_run/HOW-TO-BUILD-THE-BOOK.md`.

**Two layers, always:** the sitting HTML is the source of truth (human-reviewable,
authored once, never re-derived from the PDF again). `questions.json` and everything
downstream of it is *computed* from the HTML and can be regenerated any time the
computation logic changes, without touching a single HTML file.

- **`first_run/output/generated-from-script/`** — `questions_index.json` and every

  `generate_all_chapter_books.py`.

**Whole-book assembly is also built and proven end-to-end (2026-07-27)**: front matter,

things out of order or half-finishing a change.

## 4. Why difficulty (Easy/Medium/Hard) is computed in Python, not authored in HTML

Pranav's rule: difficulty is derived from **the number of distinct topics tagged on a
question** — up to 2 topics = Easy, 3–5 = Medium, more than 5 = Hard. This lives in the
`questions.json`-building Python script, never as a hand-written attribute in the sitting
HTML, for one concrete reason: the thresholds or the label names (`Easy/Medium/Hard` vs.
something else) will change the first time someone eyeballs real results, and a Python
rule is a one-line edit — a hand-authored HTML attribute would mean revisiting every
question in every sitting file. This is the same reasoning that already governs the
two-layer split above: HTML is authored once by a human/AI and stays stable; anything
that might need recomputing lives in code.

## 6. Non-negotiable cross-cutting rules (apply regardless of which skill you're using)

1. **Verbatim, always.** Question and answer content is transcribed exactly as printed —
   every number, every rupee sign, every table cell. Reformatting messy OCR into clean
   HTML is required; changing what it *says* is never allowed.
2. **Flag uncertainty, never guess silently.** A genuinely ambiguous OCR table, a source
   answer key with an internal inconsistency, an unindexed topic — all get an explicit
   flag (`data-issue`, an `.extraction-note`), never a silent best-guess presented as
   confident fact. This is an accounting reference book — a wrong number is costly to a
   student, not just embarrassing.
3. **Don't invent a new ID scheme.** The syllabus taxonomy join keys (`unitCode` +
   `subtopicRef`) are already settled after a real migration fight (see
   `SKILL-question-bank-topic-tagging.md` §2). Every new attribute this pipeline adds
   references those same keys — it never introduces a parallel numbering system.
4. **HTML is authored once; JSON is always regenerable.** If a piece of information might
   need its computation logic changed later (difficulty, duplicate grouping, chapter
   placement for a *connected* multi-topic question), it belongs in the Python layer, not
   hard-coded per file.
