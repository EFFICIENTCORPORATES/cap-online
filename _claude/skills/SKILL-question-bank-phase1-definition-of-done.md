## 0. Bar relaxed 2026-07-26 — read this before applying §1 below

After the MCQ audit (§1) found and fixed 6 real errors across 67 rows, Pranav explicitly
dialed back the bar for the remaining 69 descriptive rows and for all future sittings:
*"we need not be 100% accurate... this is first edition so we can have some room for
errors... just skim through... and let's close this."* The revised, current standard:

- **Descriptive answers**: verify the pasted answer matches the ICAI answer key
  (transcription fidelity) — do **not** independently re-derive the underlying accounting
  logic step-by-step the way §1 required for MCQs. A fast automated skim for red flags
  (hedge phrases, placeholder text, suspiciously short answers) plus spot-checking anything
  that stands out is sufficient.
- **The book now carries an explicit disclaimer** (front and back of every chapter book,
  see `generate_chapter_book.py`'s template) inviting readers to report errors by email,
  with an acknowledgement that this is a first edition and may contain mistakes. This
  disclaimer is the actual safety net now — not pre-publication perfection.
- **MCQs still get the full §1 treatment** (independent arithmetic re-derivation) — Pranav
  did not relax the MCQ bar, only the descriptive one, and only after seeing what the MCQ
  audit had already caught.
- **Examiner's Comment vs. Author's Note**: renamed in the rendered book (not just the
  underlying `data-comment-source` enum) — real ICAI-sourced comments are labelled
  "Examiner's Comment"; every synthesized one is labelled "Author's Note" with an explicit
  caveat that it "may not apply in every case." This is a rendering change in
  `generate_chapter_book.py`, done alongside this bar-relaxation.

## 1. Accuracy audit — MCQs only get this full treatment; descriptives use §0's lighter bar

**Scope:** every AI-authored explanation/paragraph in every sitting HTML file — not just
MCQs, not just one chapter.

**Method:**
1. For every MCQ whose source answer key is letter-only (the common case — see the
   verbatim-extraction skill §6), independently re-derive the arithmetic from the
   question's own figures and confirm it lands on the stated `data-answer` letter. Do not
   accept a fluent-reading explanation at face value, including one already marked
   `review-status="verified"`.
2. For every descriptive answer, spot-check at least the key figures against the source
   PDF (per the existing verbatim-extraction skill §2–4).
3. **Where the correct accounting treatment itself is in doubt** (not just arithmetic, but
   *which rule applies*), consult the ICAI study material directly:
   **`books/concept-book/raw_icai_study_materials/`** — one `.md` per syllabus unit,
   named `M{module}_C{chapter}_U{unit}_ {Title}.md` (e.g.
   `M2_C5_U1_ Accounting Standard 2 Valuation of Inventory.md`). This is the authoritative
   rule text for the whole syllabus — use it to settle a doubt, never guess or infer a
   rule from the question's phrasing alone.
4. Any explanation found wrong: fix it, fix the attached Common Student Mistakes note if
   it was inverted along with it (this happened both times in the 2026-07-26 incident —
   check it every time, don't assume only the main explanation needs correcting), and
   rewrite the `extraction-note` to honestly state what's verbatim (letter/options/figures)
   vs. AI-authored (the explanation), tagging `data-issue="answer-key-letter-only"` where
   applicable.
5. Any explanation confirmed correct on re-derivation still gets its `extraction-note`
   corrected if it was previously mislabeled "verbatim... confidence high" for authored
   content — the metadata must be honest even when the content was already right.

**This is a gate, not a nice-to-have:** a sitting/chapter is not "done" until every one of
its rows has been through this pass — mark this explicitly (e.g. a tracking note per
sitting file, or a checklist in the project log) as sittings are cleared, since 5 files ×
~27 rows each is enough that it's easy to lose track of which have actually been
re-verified vs. merely re-read.

## 2. Cross-chapter classification — finalized design (resolves the earlier open issues 2 & 3)

Pranav's instruction, now locked as the rule: when a case-scenario cluster's sibling MCQs
(or a single connected descriptive question) collectively touch **more than one chapter**,
the full content lives in exactly **one home chapter** — whichever touched chapter is
taught **latest** in `teaching_sequence` (same direction as the existing Final Chapter
rule, extended from single questions to whole clusters). That home chapter shows it under
a distinct **"(b) Integrated with Other Standards"** sub-heading, separate from ordinary
single-AS questions. Every *other* chapter the cluster touches gets a short cross-reference
line only ("This case scenario also tests AS 11 — see that chapter's Integrated section"),
**never the full duplicated content**.

This one rule resolves three previously-separate open issues at once:
- **Case-scenario duplication** (a shared scenario is now stated once, in its home chapter,
  with all sibling MCQs nested beneath it — never repeated per MCQ).
- **Cross-chapter cluster homing** (the P Limited cluster: AS 11 taught later than AS 2 →
  homes entirely to AS 11; AS 2's book gets a pointer, not a full copy of Q4).
- **Single-AS vs. Integrated sub-buckets** (every chapter's Sections I and II split into
  "(a) Single-AS" and "(b) Integrated with Other Standards," using this same rule).

**Implementation consequence, not yet built:** `extract_questions.py` needs a clustering
pass (group qblocks by shared `data-case-ref`; for a cluster spanning >1 chapter, compute
one cluster-level home chapter and treat every sibling's placement accordingly — this may
override an individual MCQ's own `data-final-chapter` computed in isolation).
`generate_chapter_book.py` needs: nested case-scenario rendering (once per cluster, not
once per MCQ), the (a)/(b) sub-heading split, and the cross-reference box for non-home
chapters. Do this **after** the accuracy audit (§1) is clean for the sittings involved —
building new rendering logic on top of unverified content wastes the work if the content
underneath still needs fixing.

## 3. Theory vs. Practical — fold into the audit pass, don't run separately

`data-qtype` (`theory`/`practical`) already exists on every descriptive qblock. While
doing the accuracy audit (§1) on a descriptive question, also sanity-check its existing
`theory`/`practical` tag against Pranav's heuristic (verbose/text-driven with little or no
computation ⇒ theory) and fix any mistagging found. Then surface the tag in the chapter
book's `qmeta` line (a rendering change, bundle with §2's regeneration). Don't schedule
this as a separate pass — it's nearly free once you're already reading the question for §1.

## 4. Two external-review suggestions accepted as genuinely high value

Everything else from the external AI's 12-point list is explicitly parked (see
`SKILL-question-bank-chapter-book-rendering.md` — update that skill's open-issues list to
mark 3.2/3.3 as **resolved** by §2 above once implemented, rather than duplicating the
design here). Only these two were accepted into Phase 1:

- **Remove build/engineering plumbing from student-facing text** — the scope note
  currently names scripts, JSON files, and folder paths. Move that to a separate
  "build info" footer, keep the student-facing scope note in plain outcome language
  (question count, what's covered/excluded and why — not *how* it was built).
- **Fix the Mistakes-box voice for MTP/RTP** — "Many examinees..." is a factual claim
  about real candidates that is **false** for MTP/RTP sittings, which never had any
  (only PYQ sittings had real candidates; only 6 of those have a real ICAI comment at
  all — see `SKILL-question-bank-examiner-comments.md`). Rephrase synthesized comments
  on MTP/RTP material to avoid asserting real examinee behavior (e.g. "A common error
  here is..." rather than "Many examinees..."). This is a correctness fix, not a tone
  preference — it was masquerading as a UX nitpick but is actually the same
  provenance-honesty issue as §1's extraction-note fix.
- (Essentially free, bundled with §2/§3's regeneration, not really a separate decision):
  render the topic tag's existing `data-subtopictitle` value instead of just the bare
  ref number — the data already exists, this is display-only.
